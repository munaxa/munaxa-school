# Accessibility

## Overview
Munaxa targets WCAG 2.2 AA across admin, parent, teacher, and mobile experiences. Accessibility is a release criterion, not an optional polish pass.

## Usage
- Use semantic HTML before ARIA and preserve heading order.
- Every interactive control must work by keyboard with a visible `:focus-visible` indicator.
- Maintain at least 4.5:1 contrast for normal text and 3:1 for large text and meaningful UI graphics.
- Give form controls visible labels; connect help and error messages using `aria-describedby`.
- Use real table headers with `scope`, a caption or accessible name, and announced sort state.
- Announce asynchronous success and failure through a polite live region; move focus only when context changes.

## Examples
```tsx
<label htmlFor="student-search">Search students</label>
<input id="student-search" aria-describedby="student-search-help" />
<p id="student-search-help">Search by name or student ID.</p>
```

## Best practices
Test keyboard order, screen-reader names, zoom at 200%, forced colors, reduced motion, loading states, and all validation paths. Icon-only buttons need an accessible label; color-coded statuses need text.

## Accessibility notes
Automated tests catch only a subset of issues. Add manual keyboard and screen-reader checks to acceptance criteria.

## RTL notes
Focus order follows DOM task order, not visual direction. Verify mixed-language accessible names and announcements with an Arabic screen reader voice.
