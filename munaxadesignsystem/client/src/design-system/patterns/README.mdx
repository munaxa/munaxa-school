# Product patterns

## Overview
Patterns define repeatable school-operation workflows above the component level. They constrain hierarchy and behavior while leaving room for role-specific content.

## Usage
Use the matching pattern before composing a new screen. Each pattern must document its description, layout diagram, usage rules, do, don't, and a real school example. Canonical structured content lives in `patterns.ts` and drives the documentation UI.

## Examples
Dashboard, CRUD, Student Profile, Attendance, Finance, Reports, Settings, Empty States, Loading States, and Error States are included.

## Best practices
Choose patterns by user decision and workflow, not by visual resemblance. When a workflow materially differs, document the decision before adding another pattern.

## Accessibility Notes
Patterns include focus flow, state announcements, semantic structure, and recovery behavior.

## RTL Notes
Pattern diagrams describe logical order. Layout implementations must use logical positioning and be tested with Arabic data.
